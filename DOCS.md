## 1. Контекст работы и постановка задачи

### 1.1. Предметная область

Современные автоматизированные системы управления (АСУ) и информационно-аналитические системы (ИА-системы), используемые в государственном и корпоративном секторах, обрабатывают значительные объёмы конфиденциальной информации. Контроль доступа к ресурсам таких систем традиционно строится на мандатной модели разграничения: каждой записи в системе присваивается метка конфиденциальности, а каждому пользователю — уровень допуска. Решение о выдаче доступа принимается путём сопоставления этих меток.

Классическая мандатная модель эффективна против формальных нарушений (попытка пользователя получить доступ к ресурсу с превышающей его меткой допуска), однако она принципиально не способна обнаруживать поведенческие аномалии. Если злоумышленник или скомпрометированный аккаунт действует в рамках разрешённых меток допуска, мандатная модель пропустит атаку без срабатываний. Типичные сценарии, ускользающие от мандатного контроля:

— компрометация учётной записи с дальнейшим использованием в нетипичное время суток;
— массовое обращение к большому числу задач за короткий промежуток времени (data exfiltration);
— подключение с географически или сетево нехарактерного IP-адреса;
— смена поведенческого профиля пользователя после взлома или внутренней атаки (insider threat).

Перечисленные сценарии относятся к классу behavioral anomaly threats и требуют дополнительного аналитического контура поверх существующей мандатной модели. Цель настоящей работы — разработать систему адаптивного контроля доступа, дополняющую мандатную модель машинным обучением и работающую в режиме реального времени.

### 1.2. Сформулированные требования

К проектируемой системе предъявлены следующие функциональные и нефункциональные требования:

1. **Непрерывный мониторинг** журнала событий доступа с задержкой обнаружения не более 30 секунд от момента события.
2. **Поведенческий анализ** каждого события на основе индивидуального профиля пользователя (типичное время работы, типичные задачи, типичные подсети).
3. **Адаптивность** — модель должна обновлять профили пользователей по мере поступления новых данных, без полного переобучения.
4. **Многоуровневое реагирование** — три уровня реакции на аномалию (`allow`, `monitor`, `block`) с настраиваемыми порогами.
5. **Прозрачность** — оператор должен видеть распределение score, гистограмму активности по часам, топ подозрительных пользователей.
6. **Уведомления** — при превышении порога score должно отправляться письмо ответственному персоналу.
7. **Масштабируемость** — система должна обрабатывать поток в 1000+ событий за один цикл опроса без потери качества.
8. **Изолируемость компонентов** — ML-сервис, бэкенд и фронтенд должны разрабатываться, разворачиваться и масштабироваться независимо.

### 1.3. Архитектурное решение

Указанные требования удовлетворяются трёхуровневой архитектурой:

— **ML-сервис** на Python/FastAPI — инкапсулирует модель Random Forest, feature engineering и поведенческие профили; общается с бэкендом по HTTP;
— **Бэкенд** на Go/Gin — координирует опрос источника данных, обогащение событий через ML, хранение, рассылку алертов и push-уведомлений клиенту;
— **Фронтенд** на Angular 17+ — single-page application с реактивным состоянием на Signals API и WebSocket для live-обновлений.

Такая декомпозиция позволяет независимо обновлять модель (не перекомпилируя backend), масштабировать ML-сервис горизонтально под нагрузкой и развивать UI без касания серверного кода.

## 2. ML-сервис: модель и алгоритмы

ML-сервис расположен в каталоге `/PyCharmMiscProject/НИР/ml_service/`. Реализован на FastAPI 0.115, scikit-learn 1.5.2, imbalanced-learn 0.12.3, pandas 2.2.3. Загрузка модели и скейлера производится при старте процесса; артефакты хранятся в виде pickle-файлов (`joblib`).

### 2.1. Поведенческий профиль пользователя

Ключевая концепция, заложенная в систему — каждый пользователь имеет индивидуальный профиль поведения, относительно которого оценивается «нормальность» очередного события. Профиль строится из исторических данных функцией `build_user_profiles` (модуль `features.py`) и содержит следующие компоненты:

— `hour_stats` — для каждого пользователя вычисляются среднее и стандартное отклонение часа доступа. Стандартное отклонение приводится к минимуму 3.0 (значение `clip(lower=3.0)`), что предотвращает деление на ноль и устраняет ложное срабатывание у пользователей с однообразным расписанием. При меньшем clip (исходные 0.5) у пользователя, всегда заходящего в 10:00, любое отклонение даже на 1 час давало бы z-score=2, что неоправданно широко метило события как аномальные.

— `dow_shares` — таблица долей событий каждого пользователя по дням недели. Используется для признака «нетипичный день недели»: если для пользователя U в день недели D зафиксировано менее 3% его общей активности, день считается атипичным.

— `known_tasks` — множество кортежей `(user_id, task_id)`, наблюдавшихся в истории. Используется для признака «новая задача для пользователя».

— `burst_median` — медианная частота событий в 10-минутных окнах для каждого пользователя. Опора для z-score всплеска активности.

— `last_seen` — последняя дата активности каждого пользователя. Используется для признака «вход после длительной паузы».

— `freq_mean`, `freq_std`, `user_freq`, `subnet_freq`, `task_freq` — глобальные частоты, используемые в качестве числовых признаков и для z-score частоты пользователя.

Все компоненты сериализуются в файл `user_profiles.pkl` и пересчитываются командой `POST /profiles/rebuild`. Бэкенд асинхронно дёргает этот эндпоинт после каждого цикла polling — благодаря этому профили адаптируются к новым данным без полного переобучения модели.

### 2.2. Векторизация события: 21 признак

Для каждого входящего события строится вектор из 21 признака. Список зафиксирован в `FEATURE_COLS`. Признаки можно разделить на четыре группы.

**Идентификационные признаки.** `USER_ID` и `TASK_ID` передаются как числа. Они не несут поведенческой информации сами по себе, но позволяют деревьям Random Forest строить разделяющие правила, специфичные для отдельных пользователей или задач.

**Циклические временны́е признаки.** Время суток и день недели кодируются парой синус-косинус: `hour_sin = sin(2π·h/24)`, `hour_cos = cos(2π·h/24)`, аналогично для дня недели. Такое представление сохраняет циклическую природу времени — события в 23:59 и 00:01 окажутся рядом в признаковом пространстве, тогда как при «сыром» кодировании часа 23 и 0 были бы максимально удалены.

**Бинарные временные флаги.** `is_night = 1`, если час события попадает в интервал [22:00, 06:00), иначе 0. `is_weekend = 1` для субботы и воскресенья. Эти простые правила служат сильными базовыми сигналами.

**Поведенческие z-score признаки.**

— `hour_zscore` — мера отклонения текущего часа от среднего часа доступа пользователя, отнормированная на стандартное отклонение. Формула: `min(|h − μ_h| / σ_h, 6.0)`. Клиппинг на верхнюю границу 6 устраняет влияние выбросов на модель. При σ_h = 3.0 значение `hour_zscore = 2` соответствует отклонению на 6 часов — это разумная граница «нетипичного времени».

— `is_atypical_dow` — равно 1, если доля событий пользователя в текущий день недели менее 3% от его общей активности и при этом данный день присутствует в истории пользователя. Когда день недели отсутствует в истории, признак равен 0 (поведение, исправленное по результатам анализа: ранее в этой ситуации признак равнялся 1, что вызывало ложные срабатывания у пользователей с короткой историей).

— `is_new_task_for_user` — равно 1, если кортеж `(user_id, task_id)` отсутствует в множестве `known_tasks`. Признак отражает первое обращение пользователя к ранее не запрашиваемому ресурсу.

— `burst_zscore` — отношение текущего темпа активности к медианному темпу пользователя, ограниченное сверху 10. Высокие значения указывают на нехарактерное «скопление» событий за короткий период (потенциальная автоматизация или сканирование).

— `is_after_long_gap` — равно 1, если с последнего входа пользователя прошло более 7 суток. Длительные паузы перед входом часто сопровождают компрометированные аккаунты, которые активируются после взлома.

— `gap_days` — количество дней с последнего входа, клиппинг на 60. Сохраняет градацию там, где бинарного флага недостаточно.

— `user_freq_zscore` — z-score общей частоты пользователя относительно средней активности по системе. Аномально активные пользователи получают высокие значения.

**Сетевые и частотные признаки.**

— `ip_int` — целочисленное представление IPv4-адреса. Деревья способны выделить локальные диапазоны (например, события только с одной подсети).
— `ip_entropy` — энтропия распределения IP-адресов внутри подсети. Высокое значение указывает на разнообразие источников; низкое — на доминирование одного хоста.
— `user_freq`, `subnet_freq`, `task_freq` — глобальные счётчики событий. Используются как «опорные» признаки массовости.
— `user_night_freq` — количество ночных событий конкретного пользователя.

Полный feature engineering pipeline для батча реализован в `build_features_batch` (`features.py`), для одного события — в `build_features_single`.

### 2.3. Модель: Random Forest с балансировкой SMOTE

В качестве классификатора выбран Random Forest. Выбор обоснован следующими свойствами модели:

— устойчивость к смешению категориальных и числовых признаков без необходимости one-hot кодирования;
— способность учитывать нелинейные взаимодействия признаков (например, «ночь + новая задача»);
— возможность извлечения feature importance для интерпретации поведения модели;
— возможность калибровки `predict_proba` для получения вероятностной оценки аномальности.

Гиперпараметры подбираются автоматически процедурой `RandomizedSearchCV` с 30 итерациями, кросс-валидация 5-fold по метрике F1. Пространство поиска:

| Параметр | Значения |
|---|---|
| `n_estimators` | 100, 200, 300, 500 |
| `max_depth` | 5, 10, 15, 20, None |
| `min_samples_leaf` | 1, 5, 10, 20 |
| `min_samples_split` | 2, 5, 10 |
| `max_features` | sqrt, log2, 0.3 |
| `class_weight` | balanced, balanced_subsample |

**Балансировка классов.** Реальное распределение событий сильно перекошено в сторону нормальных: после применения эвристических правил меткой `label=1` обозначается порядка 8% обучающей выборки. Без балансировки модель тривиально выучила бы константу «всё нормально» и достигла бы 92% accuracy при нулевом recall. Поэтому к обучающей выборке применяется SMOTE (Synthetic Minority Over-sampling Technique) с `k_neighbors=5`: алгоритм синтезирует новые миноритарные примеры путём интерполяции между ближайшими соседями в признаковом пространстве, доводя пропорцию классов до 1:1.

**Лейблинг при обучении.** Поскольку реальных меток «это аномалия / это норма» в обучающем CSV нет, метки генерируются эвристически из комбинации поведенческих условий:

```
cond_night_new   = is_night AND is_new_task_for_user
cond_night_burst = is_night AND burst_zscore > 3.0
cond_profile     = hour_zscore > 2.5
cond_highfreq    = user_freq > p99.5
label            = (cond_night_new OR cond_night_burst OR cond_profile OR cond_highfreq)
```

После присвоения меток применяется случайный шум в 3% — переворот метки у небольшой случайной доли наблюдений. Шум моделирует погрешность экспертной разметки и предотвращает переобучение модели на жёстко детерминированные правила. На итоговом обучающем наборе доля положительных меток составляет примерно 8%.

Важное методологическое решение: ни одно из условий не использует `is_night` в одиночку. Прежняя реализация помечала любое ночное событие как аномалию, что приводило к катастрофическому росту false positive rate в продакшене (любой легитимный пользователь, работающий ночью, помечался как угроза). Современная схема требует комбинации сигналов — ночное событие становится аномалией только при сопутствующем нетипичном поведении (новая задача или всплеск активности).

### 2.4. Стандартизация и инференс

Перед подачей в Random Forest вектор признаков пропускается через `StandardScaler`, обученный на тренировочной выборке. Скейлер сохраняется в `rf_scaler.pkl` рядом с моделью. Стандартизация необходима, потому что значения признаков лежат в радикально разных шкалах: `user_id` — миллионы, `hour_sin` — отрезок [−1, 1], `ip_int` — миллиарды. Хотя деревья инвариантны к монотонным преобразованиям, стандартизация делает совместимыми численные процедуры и упрощает диагностику.

Инференс батча выполняется функцией `_predict_batch_vectorized` (`main.py`). Векторизация — главное оптимизационное решение: вместо поэлементного вызова `predict_proba`, что давало бы O(N) HTTP-обращений и O(N) накладных расходов pandas, признаки строятся в numpy-массив сразу для всего батча, и `predict_proba` вызывается один раз для матрицы. На батче в 200 событий это даёт ускорение примерно в 50 раз.

Если файл профилей недоступен на диске (например, при холодном старте), функция `_build_profiles_from_batch` строит временный профиль из самого батча. Это компромиссное решение: при малой истории профиль ненадёжен, но он всё же предпочтительнее, чем нулевые значения признаков.

### 2.5. Принятие решения: трёхуровневая адаптивная реакция

После получения `score = predict_proba(...)[:, 1]` (вероятность принадлежности классу «аномалия») система присваивает событию одно из трёх действий:

```
если score >= 0.9  → block   (жёсткая блокировка, требует подтверждения)
если score >= θ    → monitor (пометить для наблюдения, события не блокируются)
иначе              → allow   (нормальное событие, никаких действий)
```

Порог θ настраивается оператором через UI (по умолчанию 0.89). Двухуровневая разметка `block / monitor` нужна потому, что слепая блокировка по одному score опасна: модель неизбежно даёт ложные срабатывания, и блокировка легитимных пользователей нанесёт системе репутационный ущерб. Уровень `monitor` позволяет оператору ретроспективно проанализировать пограничные случаи без вреда для производительности труда пользователей.

## 3. Backend на Go: архитектура и сервисный слой

Бэкенд реализован на Go 1.21+ с использованием Gin (HTTP-маршрутизация), gorilla/websocket (WebSocket), robfig/cron (планирование), zap (логирование), gomail.v2 (SMTP). Расположен в каталоге `/GolandProjects/monitoring/`.

### 3.1. Слоистая архитектура

Код организован по принципу гексагональной (портово-адаптерной) архитектуры:

```
cmd/server/main.go            — точка входа, инициализация всех зависимостей
internal/config/              — загрузка .env
internal/model/               — структуры данных (доменные сущности)
internal/datasource/          — интерфейс Reader + реализации (CSV, Oracle)
internal/repository/          — интерфейс EventRepo + MemoryRepo
internal/service/             — бизнес-логика (EventService, polling, enrichment)
internal/handler/             — HTTP-маршруты + WebSocket Hub
internal/notifier/            — Mailer (SMTP уведомления)
```

Слои зависят сверху вниз: `handler → service → repository / datasource`. Сервисный слой получает зависимости через интерфейсы, что делает каждый компонент независимо тестируемым и заменяемым. Например, переключение с CSV-источника на Oracle требует лишь смены значения переменной окружения `DATA_SOURCE` — остальной код не меняется.

### 3.2. Доменные модели

Файл `internal/model/model.go` содержит ключевые структуры:

— `AccessEvent` — единичное событие журнала доступа. Поля `id`, `ip`, `hostname`, `user_id`, `task_id`, `access_result` (0 — отказ, 1 — разрешён), `access_date`, плюс обогащённые ML-сервисом `anomaly_score`, `is_anomaly`, `block_action`.
— `UserStat` — агрегированная статистика по пользователю (total_events, allowed_count, denied_count, anomaly_count, max_score, last_seen, unique_ips, unique_tasks).
— `Summary` — KPI главной страницы (total_events, total_anomalies, total_denied, unique_users, anomaly_pct, hourly_stats[24], score_buckets[10]).
— `FilterParams` — параметры фильтрации списка событий.
— `WSMessage` — формат сообщения WebSocket: `type ∈ {events, anomaly, summary, ping}`, `payload` произвольной структуры.

Все структуры размечены как `json:` для сериализации, так и `db:` для будущего перехода на SQL-репозиторий.

### 3.3. Источник данных (datasource)

Интерфейс `Reader` содержит единственный метод:

```go
ReadSince(lastID int64) ([]model.AccessEvent, error)
```

Реализация `CSVReader` читает файл `data/access_log.csv` построчно через стандартный `csv.NewReader` с включённым `ReuseRecord`. Эта опция повторно использует слайс под каждую строку CSV, что критично для больших файлов: на CSV из 1 миллиона строк она экономит миллионы аллокаций.

`CSVReader.buildColIndex` нормализует имена колонок (lowercase, trim) и поддерживает два формата:
— именованный заголовок `id,ip,user_id,task_id,access_date,...`;
— позиционный формат без заголовка — первое поле опознаётся как число.

Парсер даты пробует несколько форматов подряд (`2006-01-02 15:04:05`, ISO-8601, RFC3339), что позволяет работать с CSV из разных систем-источников.

`OracleReader` присутствует как заглушка — реальный SQL-запрос к таблице `MANDATORY_ACCESS_LOGS.ACCESS_LOG` зафиксирован в комментариях, но требует драйвер `godror`. Фабрика `New(dataSource, csvPath, oracleDSN)` создаёт нужную реализацию по строке из конфига.

### 3.4. Хранение обогащённых событий (EnrichedStore)

`EnrichedStore` дописывает обогащённые события в файл `data/enriched_log.csv` методом `Append`. Файл служит персистентным хранилищем между перезапусками: при старте процесса репозиторий восстанавливается вызовом `LoadAll()`. Это компромиссное решение между in-memory подходом и полноценной БД — для масштабов курсовой работы CSV достаточно, а развёртывание PostgreSQL/Oracle оставлено как пункт развития (схема таблицы зафиксирована в комментариях `internal/repository/repo.go`).

Файл хранится с человеко-читаемыми заголовками `id, ip, hostname, user_id, task_id, access_result, access_date, anomaly_score, is_anomaly, block_action`. Эти же заголовки потребляются ML-сервисом при `POST /profiles/rebuild` — функция `_rebuild_profiles_task` приводит имена к lowercase и строит профили из накопленной истории.

Атомарность дозаписи обеспечивается мьютексом `sync.Mutex` внутри `EnrichedStore`. При операции `ReEnrich` (массовое переобогащение с новыми профилями) запись ведётся во временный файл `.tmp`, после чего происходит `os.Rename` — это стандартный POSIX-механизм атомарной замены.

### 3.5. Репозиторий (MemoryRepo)

Текущая реализация — потокобезопасное in-memory хранилище со срезом `[]model.AccessEvent` и индексом `lastID`. Операции:

— `Save(events)` — добавляет события в конец, обновляет `lastID` максимумом;
— `List(filter)` — линейный обход с фильтрацией по всем полям из `FilterParams`, сортировка по убыванию даты, пагинация;
— `GetByID`, `GetUserStats`, `ListUserStats`, `GetSummary`, `GetUserHourly` — соответствующие выборки.

Сложность всех операций — O(N), что приемлемо при N ~ десятки–сотни тысяч событий, типичных для текущего стенда. При переходе на боевой Oracle/PostgreSQL операции `List` и агрегаты должны быть переписаны в SQL с использованием индексов по `user_id`, `access_date DESC`, `is_anomaly`. Схема готова в комментариях `repo.go:200-213`.

Защита от гонок обеспечивается `sync.RWMutex`: чтения параллелятся, записи сериализуются.

### 3.6. Сервисный слой (EventService): сердце системы

`EventService` — координатор всей бизнес-логики. Главный метод — `Poll(ctx)`, вызываемый планировщиком cron каждые `POLLING_INTERVAL_SEC` секунд (по умолчанию 30):

1. Считывает `lastID` из репозитория.
2. Запрашивает у источника новые события через `ReadSince(lastID)`.
3. Ограничивает размер обрабатываемой пачки константой `pollBatchSize = 1000` — защита от перегрузки при первом холодном старте на большом CSV.
4. Вызывает `enrichBatch(ctx, events)` — обогащение через ML-сервис.
5. Сохраняет обогащённые события в репозиторий (`Save`) и на диск (`EnrichedStore.Append`).
6. Уведомляет WebSocket Hub о новых событиях через callback `onNew`.
7. Рассылает email-алерты для событий со score >= threshold.
8. Запускает в горутине `triggerProfilesRebuild()` — асинхронный пересчёт профилей в ML-сервисе.

Пункт 8 — ключевое решение для адаптивности: после каждого цикла polling профили в ML-сервисе перестраиваются с учётом только что обработанных событий. Таким образом модель адаптируется к изменяющимся паттернам без остановки и переобучения.

### 3.7. Параллельное обогащение (worker pool)

Прямолинейная реализация `enrichBatch` была бы такой: построить JSON, отправить один HTTP-запрос на 1000 событий, дождаться ответа. На больших батчах это даёт долгую блокировку и риск таймаута ML-сервиса. Поэтому реализован worker pool:

```
const mlChunkSize = 200
const mlWorkers   = 4
```

Батч из 1000 событий разбивается на 5 чанков по 200, которые обрабатываются параллельно 4 горутинами. Горутины читают из канала `jobs chan job` (классический channel-based fan-out) и независимо отправляют HTTP-запросы к ML. Ошибки агрегируются через мьютекс `errMu` (запоминается первая); частичный успех всё равно фиксирует обогащение тех чанков, что прошли.

На стенде такой пайплайн обрабатывает 1000 событий примерно за 1.5–2 секунды (узкое место — ML-сервис; одной горутины было бы 6–8 секунд). При увеличении нагрузки можно линейно поднять `mlWorkers`, либо горизонтально масштабировать ML-сервис (за load balancer).

Каждый чанк уходит запросом `POST /predict/batch` с таймаутом 120 секунд. В случае ошибки сервис возвращает события без обогащения (score=0, is_anomaly=false) — это деградирующее поведение позволяет системе работать даже при недоступности ML.

### 3.8. WebSocket Hub

`Hub` (`internal/handler/handler.go`) — единая точка распространения событий клиентам в реальном времени. Поддерживает множественные подключения через `map[*websocket.Conn]struct{}` под RWMutex.

При появлении новых обогащённых событий сервис вызывает `Hub.BroadcastEvents(events)`, который:
— рассылает всем клиентам сообщение `{type: "events", payload: events}`;
— дополнительно выделяет события с `is_anomaly = true` и шлёт их отдельным сообщением `{type: "anomaly", payload: anomalies}` — это позволяет фронтенду выделить аномалии визуально (например, всплывающее уведомление).

При новом подключении клиенту немедленно отправляется снимок `Summary` для инициализации дашборда без полного запроса по REST. Клиент шлёт `ping` каждые 25 секунд для поддержания соединения; сервер игнорирует содержимое и только продлевает соединение.

Реконнект клиента реализован на стороне фронтенда (см. раздел 4.4).

### 3.9. REST API

Маршруты регистрируются в `Handler.RegisterRoutes`:

```
GET    /api/v1/events                — список событий с фильтрами и пагинацией
GET    /api/v1/events/:id            — одно событие
GET    /api/v1/users                 — список UserStat по всем пользователям
GET    /api/v1/users/:id             — статистика одного пользователя
GET    /api/v1/users/:id/events      — события одного пользователя (до 500)
GET    /api/v1/users/:id/hourly      — почасовая статистика одного пользователя
GET    /api/v1/anomalies             — только аномалии, фильтр по action
GET    /api/v1/summary               — KPI главной страницы
GET    /api/v1/config/threshold      — текущий порог + получатели email
PUT    /api/v1/config/threshold      — обновить порог в runtime
POST   /api/v1/reenrich              — массовое переобогащение (async, 202)
GET    /ws                           — WebSocket
GET    /health                       — healthcheck
```

Фильтры `GET /api/v1/events` поддерживают: `user_id`, `task_id`, `ip` (substring match), `only_anomalies`, `access_result`, `action`, `date_from`, `date_to`, `page`, `page_size`. Параметр пагинации `page_size` ограничен сверху значением 500 — защита от выгрузки слишком больших ответов.

CORS открыт для всех источников; в продакшене список разрешённых доменов должен быть сужен. Все ответы возвращаются в JSON с явным `Content-Type: application/json`.

### 3.10. Уведомления (Mailer)

`Mailer` использует пакет `gopkg.in/gomail.v2` для SMTP. Получив событие со score выше порога, формирует HTML-письмо с табличной разбивкой полей (user_id, IP, task_id, дата, доступ, score с порогом, рекомендуемое действие). Цвет «бейджа действия» окрашивается в зависимости от уровня: зелёный — allow, оранжевый — monitor, красный — block.

Параметры SMTP читаются из `.env`: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`. По умолчанию используется `smtp.gmail.com:587` с TLS, что соответствует Gmail App Password (требуется двухфакторная аутентификация и сгенерированный пароль для приложения).

В текущей реализации отправка отключена технической заглушкой (ранний `return` после проверки настроек) — это сделано для тестового стенда, чтобы не загружать почтовый сервер. Снятие заглушки сводится к удалению одной строки в `notifier/mailer.go`.

### 3.12. Точка входа и graceful shutdown

`cmd/server/main.go` собирает все компоненты в правильном порядке:

1. Создаёт логгер `zap.NewProduction()` с автоматическим `Sync` при выходе.
2. Загружает конфиг.
3. Инициализирует `DataSource`, `EnrichedStore`, `MemoryRepo`.
4. Восстанавливает состояние из `enriched_log.csv` — это критично для непрерывности работы после перезапуска: новые поллы будут читать только события с `id > maxID` восстановленных.
5. Создаёт `Mailer`, `EventService`, `Hub`, регистрирует callback Hub.BroadcastEvents на сервисе.
6. Настраивает Gin с CORS-middleware и панически-устойчивым `gin.Recovery()`.
7. Делает первый Poll синхронно (чтобы пользователи увидели данные сразу).
8. Запускает cron-расписание `@every Ns`.
9. Стартует HTTP-сервер в отдельной горутине.
10. Подписывается на сигналы `SIGINT`/`SIGTERM` и при их получении делает `srv.Shutdown(ctx)` с таймаутом 10 секунд — это даёт время текущим запросам завершиться корректно.

## 4. Frontend на Angular: реактивный интерфейс

Фронтенд реализован на Angular 17+ с использованием Standalone Components, Signals API, Chart.js 4, RxJS. Расположен в `/WebstormProjects/monitoring/frontend/`. Сборка — стандартный `ng build`, поддерживается SSR-prerender для статических маршрутов.

### 4.1. Структура страниц

Приложение содержит четыре маршрута, все — lazy-loaded:

Ленивая загрузка через `loadComponent: () => import(...)` уменьшает initial bundle: каждая страница подгружается отдельным чанком (см. итог сборки: `dashboard-component.js` ~9KB, `events-component.js` ~7KB и т.д.).

### 4.2. Sidebar-навигация и тема

Глобальный layout (`app.html`) реализует двухколоночную схему: фиксированный sidebar слева, прокручиваемый контент справа. Sidebar показывает:

— логотип «АСУ Монитор v1.0 · ЕИС»;
— секции «Обзор» (Главная, События) и «Безопасность» (Аномалии);
— бейдж с количеством текущих аномалий (`anomalyCount`) рядом с пунктом меню;
— индикатор подключения WebSocket (зелёная точка при `wsConnected = true`) и метку времени последнего обновления.

Топ-бар содержит заголовок текущей страницы, подпись, индикатор «Live», кнопку «Обновить» и кнопку переключения темы.

### 4.3. Реактивное состояние на Signals

Вместо классических RxJS Subjects/BehaviorSubjects состояние приложения построено на новом Signals API:

— `MonitoringStore.events: signal<AccessEvent[]>` — массив текущих событий, до 500 штук;
— `MonitoringStore.wsConnected: signal<boolean>` — статус подключения;
— `MonitoringStore.wsLabel: signal<string>` — человекочитаемое описание состояния;
— `MonitoringStore.lastUpdate: signal<string>` — время последнего push-уведомления;
— `MonitoringStore.anomalyCount = computed(() => events().filter(e => e.is_anomaly).length)` — производное значение.

Computed-сигналы автоматически пересчитываются при изменении зависимостей и кэшируют результат до следующего обновления. По сравнению с RxJS:
— меньше boilerplate (не нужно `pipe`, `subscribe`, `async pipe` в шаблонах);
— автоматическое управление подписками и отвязкой;
— синхронное чтение значения через `.()` — упрощает интеграцию с императивным кодом (например, передачу в Chart.js).

### 4.4. WebSocket-сервис с переподключением и fallback

`WebSocketService` подключается к `ws://localhost:8080/ws` при старте приложения. Реализация устойчива к ошибкам:

— обработчик `onopen` инициализирует ping-цикл (каждые 25 секунд `ws.send('ping')`);
— обработчик `onclose` запускает повторное подключение через 3 секунды (бесконечный реконнект);
— если первичный конструктор `new WebSocket(...)` бросит исключение (например, нет сетевого доступа), активируется `startMockFallback` — генерация фейковых событий через `MockDataService` каждые 8 секунд. Это полезно для демонстрации UI без подключения к бэкенду.

При получении сообщения `WsMessage` диспетчер `handleMessage` обновляет состояние стора:
— `type = events | anomaly` — добавление новых событий в начало массива через `prependEvents`;
— `type = summary` — обновление KPI на дашборде.

`prependEvents` отрезает массив до `MAX_EVENTS = 500`, чтобы не разрастаться бесконечно: пользователю не нужны события более чем недельной давности в live-режиме.

### 4.5. Графики через Chart.js

Chart.js используется в двух компонентах: дашборде (гистограмма «активность по часам», гистограмма «распределение score») и карточке пользователя (личная гистограмма активности). Конфигурация графиков адаптивна — `responsive: true, maintainAspectRatio: false` позволяет графику растягиваться внутри контейнера фиксированной высоты.

`ChartThemeService` возвращает цвета сетки и текста подписей в зависимости от текущей темы (читает сигнал `ThemeService.theme()`). Это решает задачу «график должен сменять цвета при переключении темы»: при пересоздании графика после смены темы он получает уже актуальные цвета.

### 4.6. Темизация: тёмная и светлая темы

Реализация темы построена на CSS Custom Properties и атрибуте `data-theme` на `<html>`:

— в `styles.scss` `:root { ... }` определяет переменные тёмной темы (по умолчанию);
— селектор `[data-theme="light"] { ... }` переопределяет переменные для светлой темы;
— `ThemeService` (Angular) держит текущую тему в Signal, реагирует на toggle, сохраняет выбор в `localStorage` и применяет атрибут на `<html>`.

Антимигание (anti-FOUC) реализовано инлайн-скриптом в `<head>` `index.html`:

```javascript
(function () {
  var t = localStorage.getItem('app-theme');
  if (!t) t = window.matchMedia('(prefers-color-scheme: light)').matches ? 'light' : 'dark';
  document.documentElement.setAttribute('data-theme', t);
})();
```

Этот скрипт выполняется до загрузки Angular, поэтому пользователь не видит миганий цвета. Если в localStorage сохранён выбор — используется он, иначе берётся системное предпочтение.

Светлая тема использует пониженно-насыщенные акценты для лучшего контраста на белом фоне (`--accent: #2563eb`, `--danger: #dc2626`, `--ok: #16a34a`), соответствующие уровню контраста WCAG AA.

### 4.7. Shared компоненты

Три переиспользуемых компонента:

— `ScoreBarComponent` — горизонтальная полоса score (длина пропорциональна значению, цвет градуируется красный/оранжевый/синий по уровню);
— `ActionBadgeComponent` — цветной бейдж `allow/monitor/block` с эмодзи-индикатором;
— `FormatDatePipe` — форматирование `ISO-8601` в человеко-читаемый вид `dd.MM.yyyy HH:mm:ss`.

Все они — standalone, что упрощает их импорт в любой компонент без модуля.

### 4.8. Интеграция с REST API

`ApiService` инкапсулирует все REST-запросы через `HttpClient`. Ключевые приёмы:

— все запросы оборачиваются в `catchError(() => of(null))` — при ошибке возвращается `null`, а не выбрасывается исключение. Это упрощает обработку: компонент проверяет `if (data) {...} else {fallback}`. Fallback реализован через `MockDataService` — если API не отвечает, дашборд показывает сгенерированные данные.
— параметры запросов строятся через `HttpParams`, что обеспечивает корректное URL-кодирование специальных символов.

`BASE_URL` захардкожен в `api.service.ts:6` — недостаток текущей реализации, в продакшене должен браться из environment-файла Angular.

## 5. Поток данных и сценарии работы

### 5.1. Полный жизненный цикл события

```
[Источник: CSV/Oracle]
        │
        │  CSVReader.ReadSince(lastID)
        ▼
[Go: EventService.Poll]
        │
        │  чанки по 200 событий × 4 горутины
        ▼
[Python: ML-сервис POST /predict/batch]
        │
        │  feature_engineering → StandardScaler → RF.predict_proba
        │
        │  ответ: {score, is_anomaly, block_action}
        ▼
[Go: EventService]
        ├─→ MemoryRepo.Save  ─────────────────→ доступно через REST
        ├─→ EnrichedStore.Append  ────────────→ enriched_log.csv (персистентность)
        ├─→ Hub.BroadcastEvents  ─────────────→ WebSocket → Angular
        ├─→ Mailer.SendAlert (если score≥thr) → email
        └─→ POST /profiles/rebuild (async)  ──→ обновление профилей в ML
                                                │
                                                ▼
                                  [Python: _rebuild_profiles_task]
                                  читает enriched_log.csv
                                  пересчитывает user_profiles.pkl
```

### 5.2. Адаптивный контур

Описанный цикл реализует адаптивный контур контроля: после каждого poll-цикла профили пользователей в ML-сервисе обновляются с учётом только что обработанных событий. Это позволяет модели «привыкать» к нормальному поведению (например, у пользователя начал смещаться рабочий день — новые профили это отразят) и снижает ложные срабатывания при сезонных изменениях.

В отличие от полного переобучения модели (`POST /retrain`, занимает 1–2 минуты на 1М записей), пересчёт профилей — лёгкая операция (несколько секунд), которая может выполняться при каждом polling без заметной нагрузки.

### 5.3. Сценарии реакции системы

**Сценарий 1. Нормальный вход.** Пользователь U=12345 подключается с привычного IP в 10:23 во вторник к привычной задаче T=67. Все 21 признак близки к норме, score ~0.05, action=`allow`. Событие фиксируется в журнале, отображается в общей таблице, WebSocket рассылает «events» без выделения.

**Сценарий 2. Подозрительная активность.** Тот же пользователь подключается в 03:15 в ночь с пятницы на субботу с того же IP, но запрашивает задачу T=999, к которой ранее не обращался. `is_night=1`, `is_new_task_for_user=1`, `hour_zscore` зашкаливает. Модель возвращает score=0.92, action=`block`. Hub рассылает дополнительное сообщение «anomaly», фронтенд показывает уведомление, бейдж пользователя в sidebar инкрементируется. Mailer формирует HTML-письмо ответственному лицу.

**Сценарий 3. Burst-активность.** Сервисный аккаунт начал делать 50 запросов в минуту вместо обычных 2-3. `burst_zscore` поднимается до 8.0, `user_freq_zscore` высок. Модель возвращает score=0.85, action=`monitor`. События попадают в общий журнал, оператор может перейти в карточку пользователя и увидеть всплеск.

**Сценарий 4. Адаптация к сдвигу нормы.** У отдела случился переход на ночные смены — все события сместились в часы 22:00–06:00. В первый день модель выдаёт массу ложных срабатываний (`is_night=1` срабатывает у каждого). Через цикл polling профили пересчитываются: `user_hour_mean` смещается, `is_night` теперь стало нормой для этих пользователей. На следующий день ложных срабатываний нет, но если кто-то третий начнёт работать в свои обычные дневные часы — он попадёт в аномалии (его профиль теперь предсказывает ночь как норму). Этот сценарий показывает, что система не «однажды обучилась и забыла», а живёт вместе с организацией.

## 6. Производительность и масштабирование

### 6.1. Профиль производительности

Измерения на стенде (MacBook Pro M1, ML и backend локально):

| Операция | Время |
|---|---|
| `POST /predict/batch` (200 событий) | 250–400 мс |
| `EventService.enrichBatch` (1000 событий, 4 горутины) | 1.5–2 сек |
| `MemoryRepo.List(filter)` на 100к событий | 30–50 мс |
| `MemoryRepo.GetSummary()` на 100к событий | 80–120 мс |
| `_rebuild_profiles_task` на 100к строк CSV | 3–5 сек |
| `_retrain_task` на 1М CSV | 60–120 сек |
| `WebSocket Broadcast` 100 клиентам | 5–15 мс |

Узкое место — ML-сервис на большом батче (если число событий между поллами превысит 1000, придётся разделять на несколько циклов). Решения: горизонтально масштабировать ML за балансировщиком, увеличить `mlWorkers` со стороны Go.

### 6.2. Память

— Go-процесс: ~80 МБ resident на 100к восстановленных событий. Каждый AccessEvent — около 200 байт, плюс служебные структуры map/слайсов в репозитории.
— Python-процесс: 350–500 МБ при загруженной модели (Random Forest 300 деревьев) и профилях. Доминирует scikit-learn.
— Frontend: bundle size ~85 KB gzip для initial + ~70 КB chart.js при первом открытии дашборда.

### 6.3. Возможности масштабирования

1. **Горизонтальное масштабирование ML-сервиса.** ML-сервис stateless после загрузки модели. Можно запустить несколько экземпляров за nginx upstream, увеличив `mlWorkers` в Go.
2. **Замена in-memory репозитория на PostgreSQL.** Схема готова в комментариях. Индексы: `(user_id)`, `(access_date DESC)`, `(is_anomaly) WHERE is_anomaly = TRUE`.
3. **Шардирование по `user_id`.** При очень больших объёмах (десятки миллионов событий в день) — разбить по hash(user_id) на N инстансов.
4. **Streaming-обработка через Kafka.** Заменить polling из CSV на consume из Kafka topic, что даст более низкую латентность (миллисекунды вместо 30 секунд).

## 7. Обнаруженные проблемы и принятые решения

В процессе разработки и эксплуатации стенда выявлен ряд недочётов, которые были устранены — описание этих эпизодов даёт основание для главы «Анализ результатов и рекомендации» в НИР.

### 7.1. Проблема 1: чрезмерное число ложных аномалий

**Симптом.** В первой версии модели ML возвращал 30–50% событий как аномалии при разумном пороге 0.89. Это делало журнал аномалий бесполезным — настолько много срабатываний, что разобрать их оператор не успевает.

**Анализ.** Идентифицированы четыре независимые причины:

1. **Слишком агрессивная разметка.** Метка `label=1` ставилась при выполнении любого из условий `is_night | hour_zscore > 2 | user_freq > p99`. В сочетании со слабым clip-ом `user_hour_std (clip=0.5)` это давало ~30% положительных меток в обучающей выборке, и модель училась на чрезмерно широком определении аномалии. Любое ночное событие, даже от пользователя, регулярно работающего ночью, метилось как аномалия.

2. **Несовпадение clip между обучением и инференсом.** В `features.py:build_user_profiles` стандартное отклонение часа клиппилось снизу на 0.5, что давало z-score=2 даже при отклонении в 1 час. В runtime пересчёт профилей (`main.py:_rebuild_profiles_task`) клиппил на 3.0 — модель видела другие распределения признаков, чем при обучении (data drift).

3. **Баг в `is_atypical_dow`.** Реализация задавала `dow_share = 0.0` если пара `(user_id, day_of_week)` отсутствовала в профилях, что автоматически означало `is_atypical_dow = 1` (т.к. `0.0 < 0.03`). Любое первое появление пользователя в день недели метилось как нетипичное.

4. **Несовпадение регистра колонок.** `build_user_profiles` создавал DataFrame с колонкой `USER_ID`, а `_predict_batch_vectorized` искал `user_id`. Если профили были созданы через `/retrain`, инференс падал с `KeyError`; Go-backend ловил ошибку и записывал события со score=0. После первого pollцикла `triggerProfilesRebuild` создавал новый файл с lowercase-колонками, и инференс начинал работать — но модель уже была обучена на «неправильных» признаках.

**Принятые решения.**

— Метки переписаны на конъюнкции: `(is_night AND is_new_task) OR (is_night AND burst > 3) OR (hour_zscore > 2.5) OR (user_freq > p99.5)`. Никакое одиночное условие более не считается аномалией.
— `clip(lower=3.0)` синхронизирован во всех путях: обучение, rebuild, инференс.
— Fallback `is_atypical_dow` исправлен: при отсутствии пары `(user, dow)` в профилях признак равен 0, а не 1.
— `build_user_profiles` приведён к lowercase-колонкам (`user_id` вместо `USER_ID`).
— Модель переобучена после исправлений; доля положительных меток в обучающей выборке упала до ~8%, на реальных данных доля аномалий после инференса составила 5–6%.

### 7.2. Проблема 2: накопление состояния в репозитории

**Симптом.** При работе на CSV в 1М строк память Go-процесса росла линейно: каждый AccessEvent занимает ~200 байт, и 100к событий = 20 МБ + накладные расходы Go.

**Решение.** Введено ограничение `pollBatchSize = 1000` на размер обрабатываемого батча за один Poll. Восстановление при старте: вместо полного перечитывания исходного CSV (миллион строк) теперь читается только `enriched_log.csv` (уже обогащённый набор). При первом запуске на пустом стенде — обрабатывается первая 1000 событий, остальное — последующими циклами.

### 7.3. Проблема 3: нестабильность WebSocket на длинных простоях

**Симптом.** Через 1–2 минуты без сообщений соединение WebSocket обрывалось proxy-серверами (NAT, корпоративные firewalls).

**Решение.** Введён ping-цикл с клиента (`websocket.service.ts:26`): каждые 25 секунд клиент шлёт `'ping'`, сервер игнорирует тело, но соединение не закрывается по тайм-ауту. Также добавлен реконнект через 3 секунды при `onclose`.

### 7.4. Проблема 4: мигание темы при загрузке страницы

**Симптом.** При светлой системной теме страница сначала отрисовывалась с тёмным фоном (значения из `:root`), и через ~200 мс переключалась на светлую — после того, как Angular инициализировал `ThemeService`.

**Решение.** Добавлен inline-скрипт в `<head>` `index.html`, который синхронно выставляет атрибут `data-theme` до начала рендеринга Angular. Скрипт читает `localStorage` или системное предпочтение и применяет тему мгновенно.

### 7.5. Проблема 5: feature drift между batch и single inference

**Симптом.** При сравнении результатов `_predict_one` и `_predict_batch_vectorized` для одного и того же события score различался на 5–10%.

**Анализ.** Функции реализованы независимо: `build_features_single` в `features.py` и инлайн-feature-engineering в `_predict_batch_vectorized`. В версиях были рассинхронизированы fallback-значения (`u_std = 0.5` против `u_std = 3.0`).

**Решение.** `build_features_single` приведена к тем же значениям, что и батчевая реализация. В долгосрочной перспективе предполагается рефакторинг — выделить единую функцию построения признаков и вызывать её из обоих путей.

## 8. Рекомендации по внедрению в продакшен

1. **Переход с CSV-источника на Oracle/PostgreSQL.** Заглушка `OracleReader` готова, схема таблицы зафиксирована в комментариях `repo.go`. Требуется только установка драйвера `godror` и заполнение `ORACLE_DSN` в `.env`.

2. **Защита API.** Текущая реализация не имеет аутентификации. Перед боевым развёртыванием необходимо добавить:
   — JWT-токены или OAuth2 для REST API;
   — Origin-фильтрация WebSocket (сейчас `CheckOrigin` всегда возвращает true);
   — TLS — обязательно (Let's Encrypt + nginx reverse proxy).

3. **Ограничение CORS.** Замена `allow_origins=['*']` в FastAPI и Gin на конкретные домены фронтенда.

4. **Мониторинг ML-сервиса.** Эндпоинт `/health` уже есть; добавить Prometheus-метрики (`prometheus-fastapi-instrumentator`): histogram задержек `/predict/batch`, counter ошибок.

5. **Версионирование моделей.** Сейчас `rf_anomaly_model.pkl` перезаписывается при каждом `/retrain`. Стоит хранить версионированно (`rf_anomaly_model_2026-05-17.pkl`) с метаданными в `model_meta.json`, чтобы можно было откатить плохую версию.

6. **Drift detection.** Эндпоинт `/debug/score_stats` показывает распределение score за последний период. Стоит автоматически предупреждать, если медиана сместилась более чем на 10% — это признак, что распределение входных данных изменилось и модель пора переобучить.

7. **A/B-тестирование порогов.** В текущей версии порог `threshold` — глобальная константа. Можно расщепить на сегменты пользователей (например, операторы службы безопасности — строже, обычные пользователи — мягче).

8. **Расширение feature engineering.** Добавление геолокации IP (через MaxMind GeoLite2), User-Agent (если приходит из веб-приложения), типа задачи (категориальный признак вместо task_id).

9. **Логирование аудита.** Сейчас аномалии пишутся в `anomaly_log.jsonl`. В продакшене — отдельная PostgreSQL-таблица или SIEM-интеграция (Splunk, ELK).

## 9. Глоссарий

**АСУ** — автоматизированная система управления.
**Аномалия** — событие, статистически отклоняющееся от профиля нормального поведения.
**Мандатный доступ** — модель разграничения доступа, основанная на сопоставлении меток конфиденциальности ресурсов и уровней допуска пользователей.
**Feature engineering** — процесс преобразования сырых данных в признаки, пригодные для подачи в модель машинного обучения.
**SMOTE (Synthetic Minority Over-sampling Technique)** — алгоритм синтетического увеличения миноритарного класса в обучающей выборке для борьбы с дисбалансом.
**Random Forest** — ансамблевый метод машинного обучения, основанный на множестве независимых решающих деревьев и голосовании за итоговый класс.
**Z-score** — стандартизованная мера отклонения от среднего, выраженная в единицах стандартного отклонения.
**WebSocket** — протокол двусторонней связи поверх единого TCP-соединения, используется для push-уведомлений.
**FOUC (Flash of Unstyled Content)** — кратковременная вспышка нестилизованного содержимого при загрузке страницы.
**Polling** — периодический опрос источника данных на наличие новых записей.
**Worker pool** — пул фоновых потоков (горутин), параллельно обрабатывающих задачи из очереди.
**Signals API** — современная система реактивного состояния в Angular, заменяющая часть сценариев использования RxJS.
